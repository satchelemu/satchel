# App audit, 2026-11-03

Scope: the app shell around the emulator (first launch, import, Prepare, shader warm-up,
the game page, leaving and returning to a game, app lifecycle). The emulator itself is
out of scope. Each finding names the code, says what the user sees, and gives the fix.
Priority: P1 breaks a flow the user depends on, P2 confuses or loses work, P3 polish.

Rules for whoever implements this: no em dashes or double hyphens in anything written;
keep the UI landscape-locked; keep every existing accessibility identifier that a test
still uses; the simulator suite is `python3 -B NativeApp/build.py --ui-tests-simulator`
with `SATCHEL_UI_SIMULATOR=36121A19-E9FE-4A1A-AB26-9EFEC2F095D2` and
`SATCHEL_UI_ONLY_TESTING=<test>,<test>` to keep runs short; one xcodebuild at a time.

## 1. First launch (P1, user request: remove the welcome page)

What happens: `App/HomebrewView.swift:225` opens `OnboardingView` as a full-screen cover
whenever the library and prepared list are empty and `SatchelOnboardingFinished` is
false. It is a four-step guide (welcome, keys, import one game, Prepare) with its own
single-file picker (`App/OnboardingView.swift:88`), its own progress bar that is
indeterminate for the whole download phase, and a "Continue" that stays disabled until
the game's info has been read. Settings > About links back to it (`settings-onboarding`).

Why it is wrong: the home screen already has the same three steps as its empty state
(`welcome(compact:)` at `App/HomebrewView.swift:766`: keys, add a game, prepare and
play), so the guide is a second, narrower copy of the dashboard that hides the real one.

Fix:
- Delete `App/OnboardingView.swift` and `HomeRoute.onboarding`, the `onboardingFinished`
  storage, the `onAppear` gating, `guidedPrepareAction` and the Settings `openOnboarding`
  parameter and button. First launch lands on the home screen with the empty state.
- Keep the bundled install guide: move `InstallGuideView` (same file, line 139) into
  `App/SettingsView.swift` and show it from About as "Install and refresh help"
  (identifier `settings-install-help`, sheet, close identifier `install-help-close`).
- The game page's Prepare button currently opens the generic Prepare screen with nothing
  selected (`prepareAction` at `App/HomebrewView.swift:373` opens `.prepare`). Make it
  open `.guidedPrepare(item.id)` so the game is preselected. That route already exists.
- Tests: in `Tests/UI/Navigation/NavigationJourneyTests.swift` remove the
  `testSimulatorOnboarding` special case in `setUpWithError` (line 27), and the tests
  `testSimulatorOnboardingInstallHelpBothLandscapes`, `testSimulatorOnboardingSkipAndReopen`,
  `testGuidedOnboardingSelectsBaseInPrepare`. Add one test that opens Settings > About >
  `settings-install-help`, checks `install-help-content` scrolls, and closes it. Add one
  that opens a game page with `-SatchelPreviewDLC unprepared` and checks `prepare-game`
  preselects `prepare-base` to "Lantern Drift [Base]" (the old guided test did this).
  `OnboardingDLCFixture` is a DLC fixture despite its name; leave it.
- Docs: `Tests/UI/Navigation/README.md` lines 69 to 71 and 236 to 247, `docs/testing.md`
  line 51, `ROADMAP.md` line 25 ("onboarding"), `GOALS.md` G1 "Settings and onboarding"
  and G8 "Onboarding and distribution" (keys import and install guide stay; the guide
  screen is gone).

## 2. Import runs with no background keep-alive (P1)

What happens: `HomebrewLibrary.importFile` (`App/HomebrewLibrary.swift:96`) runs the copy
on a plain dispatch queue with no `beginBackgroundTask` and no continued processing task.
Leaving the app suspends the copy at once; if iOS then ends the app, the partial
`.import-<uuid>` file is deleted on the next launch
(`SwitchPackageImport.removeInterruptedCopies`) and the user starts over. Prepare
(`NativePrepare/PrepareJob.swift:27` and `:277`) already does this correctly.

Fix: give the import the same lifetime as Prepare. Begin a background task when the
import starts and end it when it finishes. Register and submit a
`BGContinuedProcessingTaskRequest` (identifier prefix `<bundle>.prepare.` so no Info.plist
change; title "Importing <name>", subtitle the stage; strategy `.fail`; run the existing
work inside the task with `task.progress` driven from the copy callback, expiration
cancels the token) and fall back to the dispatch queue when the system declines, exactly
as `PrepareJob.start` does. Keep `cancelImport` working in both paths.

## 3. Import shows no progress while Files downloads (P1, user report)

What happens: `importProgress` stays nil until the local copy begins
(`App/HomebrewLibrary.swift:101` and `:124`). For a game that lives in iCloud, the
coordinated read (`SwitchDumpSelection.coordinated`, `App/SwitchPackage.swift:292`)
blocks for the whole download, and the UI shows an indeterminate bar with "Waiting for
Files". The onboarding screen showed even less. This is the "no progress bar" the user saw.

Fix: while the download phase lasts, run an `NSMetadataQuery` on the main thread with
scopes `NSMetadataQueryUbiquitousDocumentsScope` and
`NSMetadataQueryAccessibleUbiquitousExternalDocumentsScope`, predicate
`NSMetadataItemFSNameKey IN <selected file names>`, and publish
`NSMetadataUbiquitousItemPercentDownloadedKey` (items whose
`NSMetadataUbiquitousItemDownloadingStatusKey` is current count as 100) averaged over
the selected parts as a new `downloadFraction: Double?`. Stop the query when the first
copy progress arrives or the import ends. `ImportFlowView.stage`
(`App/ImportFlowView.swift:146`) then shows "Downloading from iCloud · 42%" with a real
bar, and "Waiting for Files" only when no provider reports progress (On My iPhone and
third-party providers). Also show elapsed time in that phase so a stall is visible.

## 4. Import result is invisible from the home screen, and it hijacks navigation (P2)

What happens: the home header shows a small pill only while importing
(`importPill`, `App/HomebrewView.swift:593`). When the import finishes with the import
screen closed, `library.selected = item` (`App/HomebrewLibrary.swift:179`) makes the home
screen open that game's page by itself (`App/HomebrewView.swift:209`), and a failure
surfaces only as a generic alert. There is no card that says "Added" or "Failed: reason".

Fix: replace the pill with an import card next to the Prepare card, built like
`PrepareJobCard` (`NativePrepare/PrepareGameView.swift:383`): while running, name,
stage, percent or download percent and a 4 point bar, with "N more waiting" when the
queue is not empty; when finished, "Added · <title>" with an Open button, "Already in your
library", "Couldn't add <name>" with the reason on two lines and a Details button that
opens the import screen, or "Import stopped"; each with a dismiss cross. Keep the result
until dismissed, like Prepare. Remove the auto-open through `library.selected` on import.
`ImportFlowView.onAppear` clears the outcome today (`App/ImportFlowView.swift:40`); move
that clear to the + entry points (`addButton`, the add tile, `choose-focused-files`,
`hero-import-homebrew`) so a card's Details tap still shows the result. Hide the card
while the import screen itself is up.

## 5. Shader warm-up disappears after the first play (P1, user report)

What happens: the warm-up panel (`WarmupPanel`, `NativePrepare/WarmupView.swift`) is
shown in two places only: the Prepare screen's status panel and the "Before you play"
screen (`NativeHost/PlayerSettingsView.swift:88`). Once a game has started in this
process, `PreparedGameView` opens straight onto the game surface
(`NativeHost/PreparedGame.swift:261`, `ready` is true when the session exists), so
"Before you play" is never shown again, and the Warm up button is disabled while
`SatchelNativeSessionStarted()` (`WarmupView.swift:36`). The home card hides a finished
warm-up (`PrepareJobSlot`, `PrepareGameView.swift:362`). Net effect: after one play
there is no way to see, resume or start a warm-up until the app is relaunched. The game
page (`App/GameDetailView.swift`) has no warm-up at all.

Also: the only persistent record is one global journal in UserDefaults
(`WarmupJob.journal`, `NativePrepare/WarmupJob.swift:49`), so the state for game A is
lost as soon as game B warms up. `WarmupRunner.run` already writes
`Documents/NativeRuntime/<titleID>/warmup/<sha256 of manifest.json>/progress.json`
(`NativePrepare/WarmupRunner.swift:44` and `:55`), which is a per-package record.

Fix:
- Add a "Shaders" panel to the game page (`GameDetailView.infoScroll`, after `journey`)
  for any item with a prepared package (`artwork.preparedPackage(for:)`), using
  `WarmupPanel(package:title:)`. Drop "Play now" there (the page has Play).
- Make `WarmupPanel` show one of: not started (one sentence on what it does, "Warm up");
  running (stage, counts, bar, elapsed, "Pause"); paused ("Resume", done count);
  complete (check mark, shader and pipeline counts, time, a quiet "Warm up again");
  partial (what was left to gameplay, "Warm up again"); failed (reason, "Try again").
  Keep identifiers `warmup-start`, `warmup-pause`, `warmup-play`, `warmup-home-card`,
  `warmup-home-dismiss`; add `warmup-status`.
- When the button cannot be used, say why under it with `SatchelDisabledReason`:
  "Quit the game to warm up shaders" (session running), "Available after preparation
  finishes", "Another warm-up is running".
- Per-package status: add `WarmupJob.status(for package:)` that returns the live journal
  when it matches, else the on-disk `progress.json` (compute the manifest digest with
  CryptoKit, lower-case hex; treat a stored "running" as paused because the app was
  ended). Hash and read on a utility queue and cache by package and manifest
  modification date; never hash on the main thread per render (the Zelda manifest lists
  100,298 files).
- Home card tap should open the game page for that package (or the play screen for a
  package with no library item), not the Prepare screen. `PrepareJobSlot` needs an
  `openWarmup: (String) -> Void` closure for that.

## 6. Warm-up stops when the app is left and does not come back (P2, user report)

What happens: `WarmupJob.start` (`NativePrepare/WarmupJob.swift:101`) asks for a
continued processing task with strategy `.fail`; when iOS declines, the foreground
fallback has only `beginBackgroundTask` (about 30 seconds), after which the expiration
handler cancels the run and the journal says "paused" exactly as if the user had pressed
Pause. A memory warning does the same (`:31`). Pressing Play also cancels it on purpose
(`prepareForPlay`), which is right.

Fix: record why a run stopped. Add `interrupted: Bool` to the journal; set it only when
the background task expiration handler (not the user, not a memory warning) cancelled
the run. Add `WarmupJob.resumeIfInterrupted()` that restarts a journal marked interrupted
when nothing blocks it, and call it from the home screen when `scenePhase` becomes
active (`App/HomebrewView.swift:200`). Tell the user in the paused stage text whether it
was paused by them or stopped by iOS.

## 7. Prepare can start while a game is paused in the background (P2)

What happens: `PrepareJob.start` (`NativePrepare/PrepareJob.swift:77`) checks the
warm-up and DLC jobs but not `SatchelNativeSessionStarted()`. `AddOnJob.start`,
`WarmupJob.begin` and `PreparedPackage.delete` all refuse while a session exists. The
Workshop menu's `busyReason` (`App/HomebrewView.swift:93`) only knows about the homebrew
interpreter. A Prepare (17 GB read, rewrite, shader copy, signing, then deleting the
originals) next to a paused game holding 3.8 GB is untested.

Fix: refuse in `PrepareJob.start` with the message "Quit the game before preparing
another." Add the same reason to `PrepareGameView.startBlocked`
(`NativePrepare/PrepareGameView.swift:98`) and to `busyReason` on the home screen.

## 8. Nothing on the home screen says a game is paused (P2)

What happens: menu > Library dismisses the game cover with the game paused in memory
(`PreparedGameView` on `state == "library"`, `NativeHost/PreparedGame.swift:288`). Back
on the shelf there is no indication; the only way back is the focused tile's Play, which
reads "Play", not "Resume". `PreparedLaunch.current` holds the package.

Fix: a "Paused · <game> · Resume" card in the home header (identifier
`paused-game-card`) that opens `.preparedPackage(PreparedLaunch.current)`. Refresh it in
`presentationEnded`, on `scenePhase` active and on `.SatchelNativeSessionDidEnd`. On the
game page and the focused tile, label Play as "Resume" when
`PreparedLaunch.current == preparedPackage.folder`.

## 9. The first-launch package check has no background keep-alive (P3)

What happens: `PreparedGameView.task` (`NativeHost/PreparedGame.swift:297`) verifies the
package (several minutes the first time, reading the whole package) and prepares the
session with no background task. Backgrounding during the check suspends it.

Fix: wrap that task body in `beginBackgroundTask` / `endBackgroundTask`.

## 10. Smaller items (P3)

- `ImportFlowView` says "Keep Satchel open" (`App/ImportFlowView.swift:120` and `:176`
  contradict each other: one says keep it open, the other says closing is fine). After
  item 2, both should say the import keeps going in the background.
- The "Warm up" copy in Prepare (`PrepareGameView.swift:134`) is one long paragraph;
  shorten once the game page owns warm-up.
- `GameDetailView.nextText` (`App/GameDetailView.swift:352`) says "Keep the app open
  while it works" about Prepare; Prepare does continue in the background, so say that.
- Remove-from-iPhone is disabled while importing with a reason; it is also refused while
  a game runs by `PreparedPackage.delete` with "Close and reopen the app, then delete",
  which is the engine's one-game-per-process limit. Leave until the session restart
  work lands (GOALS G8), but show the reason before the tap, not after.

## Round 9 follow-up, 2026-11-04

The simulator regression `testWarmupSystemStopAcknowledgedAfterReturnResumes` found a
remaining item 6 race. iOS could expire the background run, the app could become active,
and only then could the worker acknowledge cancellation. The active callback saw the
old running job and did nothing; completion then left the journal paused indefinitely.
The failing assertion was `Expected starts=2 interrupted=1; actual: starts=1 interrupted=1`.
`WarmupJob.finish` now retries interrupted recovery when the app is already active.
Both the ordinary and delayed-acknowledgement simulator journeys pass. User Pause still
stays paused after background and return. The fixture triggers the production expiration
handler and uses a synthetic runner; hardware scheduling and shader reuse need the phone.

The extended `testPausedGameCardResumes` also found an item 5 regression after Quit:
`Control must be enabled: warmup-start`. `playRequested` was set before verification
but cleared only on launch failure. A successful launch left it set for the rest of
the process, even after the native session stopped. `PreparedGameView` now releases
that request gate with `defer` on both success and failure. The native-session gate
still refuses warm-up while a game is open. The same journey checks Prepare refusal
while paused, then availability with a selected base after Quit.

Final round 9 validation: the unsigned simulator navigation build and all 72 journeys
completed on the worker's iOS 27.1 simulator, with 69 passed, no failures and three
existing intentional skips. No phone actions or real game inputs were used. The full
result bundle and exact commands are recorded in `~/SatchelBuild/uitests3/report.md`.
