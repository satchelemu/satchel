# Import and Prepare validation

The native content pipeline handles compressed PartitionFS by checking the stored
SHA-256 hash layer before expanding its raw, zero and LZ4 entries. Both routing
metadata and compressed payload pass through that verified view. The same order
already applies to compressed RomFS. ExeFS extraction verifies module bytes as
it reads them, then verifies every remaining block, including unselected files,
before returning the program. A single verified block is cached as bytes. An
evicted block is verified again on a later read.

RomFS reads batch the required uncached IVFC leaf blocks into one source read,
then check each block through its parent hash chain. A batch covers at most
2 MiB, including boundary blocks. It does not read ahead into unrelated content
or cache unverified bytes for later requests. The existing 8 MiB verified-byte
cache remains bounded.

AES-XTS section reads use the first two decrypted key-area entries and 512-byte
sector numbers relative to the section. Rights-managed or sparse XTS sections
remain explicitly unsupported. AES-CTR and CTR-EX behavior is unchanged.

Bucket trees support a second index level, including the direct offsets packed
alongside child pointers in the root. Every node, entry-set index, boundary,
record ordering and source extent is checked. Limits remain explicit: two million
records and 64 MiB of serialized table storage. Retained Swift record objects
have additional memory overhead. Empty generic trees remain unsupported; the
existing empty sparse-map handling is unchanged.

The implementation follows the installed MIT LibHac 0.19.0 `Nca.OpenStorage`,
`OpenAesXtsStorage` and `BucketTree.Builder` reference, commit
`cd4004af194a51712812c680f0a028ba9152c0f8`. The existing LibHac notice is retained in
`App/Resources/Notices`. Public field layouts are documented by
[Switchbrew NCA](https://switchbrew.org/wiki/NCA). No reference source or new
runtime dependency is added. The Ryujinx 1.3.3 source pins
`Ryujinx.LibHac` 0.21.0-alpha.116, but that assembly is not in the local dependency
snapshot; its NuGet download returned HTTP 404. Skip-layer encryption modes 5 and
6 and SHA3 integrity modes still fail explicitly. Their enum values alone do not
establish the read semantics needed for a safe implementation.

Prepare reports metadata bytes, shader-file counts, module metadata bytes,
RomFS enumeration counts, dynamic-module file scan bytes and dynamic rewrite
bytes. Startup rewrites use the first 80% of their step, reserving the remainder
for dynamic modules. These are work callbacks, not time-based animation. Long
individual codec, signing and native analysis operations still need phone timing
before claiming that every visible wait has continuous progress.

## Synthetic checks

Run outside another heavy build, under the worker's disk and RSS guard:

```sh
CONTENT_BUILD="$HOME/SatchelBuild/importer/tests" \
SATCHEL_ARCHIVE_LIBRARY="$HOME/SatchelBuild/importer/archive-macosx/libShaderArchive.a" \
zsh scripts/test_content_pipeline.sh
```

The Mac suite passed 43 executable-reader, 65 RomFS and 152 content assertions
on 2026-11-04. Fixtures contain generated bytes and synthetic keys. Coverage includes ordinary
and compressed PartitionFS with CTR and XTS, corruption of unselected content,
rechecking an evicted block after source mutation, a 1,395,373-record tree with a
second index level, malformed child nodes, truncated tables, batched reads across
512-byte and 1 MiB IVFC blocks, corrupted batches, and cancelled or
failed image writes preserving the previous destination. Discarded images must
have the same length and digest as images actually written.

## Read and time measurements

`SwitchRomFSImage.measure` performs the same composition reads, integrity checks,
serialization and hashing as `write`, without opening an output file. It does not
publish a package or test output I/O. The benchmark has no signing or execution
step. Build it with:

```sh
CONTENT_BUILD="$HOME/SatchelBuild/importer/content-benchmark" \
CONTENT_MAIN=Tools/ContentPipeline/Benchmark.swift \
SATCHEL_ARCHIVE_LIBRARY="$HOME/SatchelBuild/importer/archive-macosx/libShaderArchive.a" \
zsh scripts/build_content_parity.sh
```

Run the resulting `content-parity` executable with `BASE UPDATE KEYS TITLE_ID -`.
Use `-` for UPDATE when absent. Replace the final `-` with an image path only when
there is space for the complete image. Never do that for the Zelda measurement.
It reports elapsed wall time, selected-content `Source` bytes and read calls,
RomFS writer source bytes, image size and image SHA-256. `sourcePassEquivalent`
divides tracked reads by the authenticated base and update Program NCA sizes.
It includes partial metadata reads and is not a count of physical disk passes.
Transport discovery reads outside `Source`, OS cache effects, native rewriting,
signing and package publication are outside this content benchmark.

Measured on the shared Mac on 2026-11-04, against main `da5830f` with the same
counter and discard instrumentation. All three image lengths and SHA-256 hashes
matched main. Values are main to this change:

| Game | Tracked bytes | Read calls | Pass equivalent | Content-only seconds |
|---|---:|---:|---:|---:|
| Castlevania | 6,212,985,682 to 6,147,702,323 | 187,274 to 8,570 | 2.031155 to 2.009813 | 30.643 to 8.707 |
| Odyssey | 11,708,900,772 to 11,690,086,576 | 353,962 to 15,053 | 1.975976 to 1.972801 | 26.680 to 19.307 |
| Zelda | 35,048,200,112 to 35,002,883,568 | 1,068,785 to 143,393 | 1.983180 to 1.980616 | 43.052 to 50.614 |

Read-call reduction is deterministic for these inputs. Wall times reflect shared
CPU, disk and OS cache conditions, and Zelda was slower in this content-only run.
These timings establish neither a general speedup nor phone performance. RomFS
writer input-byte totals are unchanged; the saved bytes come from ExeFS reads.

Full unsigned Mac Prepare also matched main. Castlevania and Odyssey packages
were actually written, every file was hashed, and each package was removed before
the next run. Zelda used a private adapter of the same pipeline that discarded
RomFS output and compared every payload and manifest record without publishing a
package. No full new Zelda image or package was written.

| Game | Output checked | Full Prepare seconds, main to change | Tracked bytes, main to change | Read calls, main to change |
|---|---|---:|---:|---:|
| Castlevania | All 20 written files | 102.498 to 62.258 | 6,214,214,482 to 6,148,931,123 | 187,349 to 8,569 |
| Odyssey | All 17 written files | 25.850 to 27.627 | 11,708,900,772 to 11,690,086,576 | 353,962 to 15,053 |
| Zelda | All 17 payload/manifest records, RomFS discarded | 124.000 to 96.012 | 35,048,200,112 to 35,002,883,568 | 1,068,785 to 143,393 |

Overall progress was monotonic and finished at 1.0 in all six full runs. Current
maximum observed gaps between emitted events within a step were 0.678 seconds
for Castlevania, 0.232 for Odyssey and 1.031 for Zelda. These inputs required no
large dynamic-module scan: discovery read 1,310,720 tracked bytes for Castlevania
and zero for Odyssey and Zelda. The runs used an unsigned development signer and
no optional shader pack, so they do not validate phone signing or a long shader
copy. The shared-Mac timing caveat applies to these full runs too; unchanged
rewrite work accounts for much of the elapsed-time variation.

Keep the full encrypted Program authentication pass. It binds the routing tables
before composition; merging it with arbitrary file-order reads requires a
separately validated streaming design. RomFS hashing already shared the write
pass in main. This change removes the duplicate module extraction verification
pass. Required IVFC block reads are coalesced to reduce input read calls. Neither
change removes the second large RomFS input pass or the separate dynamic-module
discovery scan when registered modules require it.

Phone validation belongs to the orchestrator: import a base and its matching
update, run Prepare while observing each step, background and reopen its progress
card, cancel during RomFS writing, then rerun Prepare and boot. Check that failures
preserve existing packages and that metadata or dynamic-module work does not hide
behind a finished progress bar. Use a package from the phone's own signer for
loading; unsigned Mac packages are parity artifacts only.
