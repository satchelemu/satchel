# Eden source investigation: pinned2026-10-31

**Validated source research only. No Eden code, dependency, build script or asset was added to the app, and no performance claim has been tested.**

The official repository is [eden-emu/eden](https://git.eden-emu.dev/eden-emu/eden). The supplied [eden-emulator/mirror](https://github.com/eden-emulator/mirror) describes itself as the mirror and points its homepage to that official repository. Both `master` branch APIs resolved to **943f1fc76087adcfc893fb1ca3aea507df15d004** during this investigation. All links below are immutable GitHub mirror links to that same commit. The official recursive metadata tree contains5052 entries; only bounded text sources were fetched (40 locally cached files, approximately720KB, plus selected connector reads). No repository clone or game data was required.

Eden is useful here, particularly its shader compiler and concrete Horizon service implementations. It is not an existing ready-to-link no-JIT iPhone core: the inspected CPU paths and desktop Apple build assumptions require substantial integration decisions.

## Ranked reusable work

###1. Horizon service contracts and a real timezone-rule provider

The most immediate startup value is the coherent service state in [psc/time/static.cpp](https://github.com/eden-emulator/mirror/blob/943f1fc76087adcfc893fb1ca3aea507df15d004/src/core/hle/service/psc/time/static.cpp), [shared_memory.h](https://github.com/eden-emulator/mirror/blob/943f1fc76087adcfc893fb1ca3aea507df15d004/src/core/hle/service/psc/time/shared_memory.h), and [time_zone_service.cpp](https://github.com/eden-emulator/mirror/blob/943f1fc76087adcfc893fb1ca3aea507df15d004/src/core/hle/service/psc/time/time_zone_service.cpp). Their root getters0–4, copied shared handle20 and all shared-page offsets agree with the implemented phone57 model. The newer [standard_steady_clock_core.cpp](https://github.com/eden-emulator/mirror/blob/943f1fc76087adcfc893fb1ca3aea507df15d004/src/core/hle/service/psc/time/clocks/standard_steady_clock_core.cpp) independently confirms the no-adjustment continuous record we researched earlier.

The next meaningful addition, when actually requested, is timezone rules/conversion rather than inventing results from a location name. Exact interfaces include GetDeviceLocationName0, LoadTimeZoneRule4, ParseTimeZoneBinary8, ToCalendarTime100/101 and ToPosixTime201/202. [time_zone.cpp](https://github.com/eden-emulator/mirror/blob/943f1fc76087adcfc893fb1ca3aea507df15d004/src/core/hle/service/psc/time/time_zone.cpp) implements validation and conversion; [glue/time/time_zone_binary.cpp](https://github.com/eden-emulator/mirror/blob/943f1fc76087adcfc893fb1ca3aea507df15d004/src/core/hle/service/glue/time/time_zone_binary.cpp) mounts an available system archive or falls back to a synthesized archive. [system_archive/time_zone_binary.cpp](https://github.com/eden-emulator/mirror/blob/943f1fc76087adcfc893fb1ca3aea507df15d004/src/core/file_sys/system_archive/time_zone_binary.cpp) constructs that fallback from compiled NxTzdb data. This gives a concrete route to bundled, versioned timezone data without requiring a fabricated Nintendo archive.

Integration: adapt an explicit bounded rule provider and parser to our checked IPC buffers, retain our process-owned clock/UUID and readonly user persona, and test malformed rules, DST overlaps/gaps and calendar limits. The current [nx_tzdb build](https://github.com/eden-emulator/mirror/blob/943f1fc76087adcfc893fb1ca3aea507df15d004/externals/nx_tzdb/CMakeLists.txt) downloads prepared data by default; its local generation path deliberately errors, so do not invoke its build blindly. The pinned package version is230326; neither that data nor its generator has been adopted or independently audited here.

###2. Native Maxwell→IR→SPIR-V compiler

This is the strongest larger graphics candidate. Eden has a standalone `shader_recompiler` CMake target with239 source/header files, not a collection of per-game precompiled shaders. The entry is [TranslateProgram](https://github.com/eden-emulator/mirror/blob/943f1fc76087adcfc893fb1ca3aea507df15d004/src/shader_recompiler/frontend/maxwell/translate_program.h), driven by a control-flow graph and [Environment](https://github.com/eden-emulator/mirror/blob/943f1fc76087adcfc893fb1ca3aea507df15d004/src/shader_recompiler/environment.h); [EmitSPIRV](https://github.com/eden-emulator/mirror/blob/943f1fc76087adcfc893fb1ca3aea507df15d004/src/shader_recompiler/backend/spirv/emit_spirv.h) emits GPU code. [vk_pipeline_cache.cpp](https://github.com/eden-emulator/mirror/blob/943f1fc76087adcfc893fb1ca3aea507df15d004/src/video_core/renderer_vulkan/vk_pipeline_cache.cpp) demonstrates both compute and graphics call chains, including merged dual-vertex programs and runtime device profiles.

The environment requires actual instruction bytes, constant-buffer values, texture metadata, program header, stage, local/shared memory sizes, workgroup dimensions and relevant rendering state. A shader byte pointer alone is insufficient. Our captured NVN Program/resource snapshots are the appropriate input boundary. Native C++ translation to SPIR-V does not itself execute generated ARM CPU code; it could run on the phone without a CPU JIT. That does not make Eden's game CPU backend JIT-free.

Integration experiment: an isolated C ABI wrapper around a pinned native compiler target with checked environment callbacks and instruction/IR/output budgets. Feed original Maxwell fixtures through it, validate SPIR-V and compare actual guarded Vulkan output against the existing compiler paths before admitting real Programs. Compilation failures and unsupported resources must stay explicit. The target links `common`, `fmt` and `sirit`; [cpmfile.json](https://github.com/eden-emulator/mirror/blob/943f1fc76087adcfc893fb1ca3aea507df15d004/cpmfile.json) pins fmt12.1.0, sirit1.0.5 and SPIRV-Headers vulkan-sdk1.4.341.0. This requires new dependency/source/license work; no such adoption was performed.

###3. Vulkan feature/profile and resource translation references

Study [vulkan_device.cpp](https://github.com/eden-emulator/mirror/blob/943f1fc76087adcfc893fb1ca3aea507df15d004/src/video_core/vulkan_common/vulkan_device.cpp) and `vk_pipeline_cache.cpp` for capability-driven shader lowering and format/workaround decisions. This is directly relevant to our existing MoltenVK backend. Device checks mention MoltenVK exceptions for missing geometry shaders, logic operations, cull distance and wide lines; an exception or a log saying “fallback” is not proof that every required rendering operation has a correct fallback. Each relevant case still needs a real Duo fixture.

Do not wholesale graft the renderer. [video_core/CMakeLists.txt](https://github.com/eden-emulator/mirror/blob/943f1fc76087adcfc893fb1ca3aea507df15d004/src/video_core/CMakeLists.txt) ties it to core, GPU state, shader compiler, caches, decoders, Vulkan utilities and VMA3.3.0. Its bundled MoltenVK dependency is explicitly the macOS artifact from Ryujinx.MoltenVK v1.4.1-ryujinx, not an iOS library. Our already-tested iOS artifact and lifetimes should remain the authority.

###4. Correct base/update composition, separate from this title's startup

[patch_manager.cpp](https://github.com/eden-emulator/mirror/blob/943f1fc76087adcfc893fb1ca3aea507df15d004/src/core/file_sys/patch_manager.cpp) selects content by update title and enabled version and replaces ExeFS from the selected update, alongside its RomFS composition paths. [content_archive.cpp](https://github.com/eden-emulator/mirror/blob/943f1fc76087adcfc893fb1ca3aea507df15d004/src/core/file_sys/content_archive.cpp) and the content-provider stack are the associated reader boundaries. This is a useful architectural reference for a verified mounted base+patch view, not a reason to treat every NSP as an update or join files by name. Our current Castlevania gallery NSP has a different application identity and must not patch the main game.

Integration remains substantial: provenance-matched CNMT selection, relevant encrypted/sparse/relocation storage support, bounded verified reads and atomic publication of a complete mounted version. The current base-only on-phone loader must continue to say base-only until those parts are implemented and tested.

###5. CPU instruction reference, not a no-JIT replacement

[Root CMake](https://github.com/eden-emulator/mirror/blob/943f1fc76087adcfc893fb1ca3aea507df15d004/CMakeLists.txt) enables native code execution only for ARM64 Android/Linux. Apple ARM64 takes the [ArmDynarmic64](https://github.com/eden-emulator/mirror/blob/943f1fc76087adcfc893fb1ca3aea507df15d004/src/core/arm/dynarmic/arm_dynarmic_64.cpp) JIT path. Its vendored [ARM64 address_space.cpp](https://github.com/eden-emulator/mirror/blob/943f1fc76087adcfc893fb1ca3aea507df15d004/src/dynarmic/src/dynarmic/backend/arm64/address_space.cpp) emits ARM blocks into code memory and changes code protection. The separate Lagoon package is selected for LoongArch64 only; it is not the Apple CPU backend.

The tempting `nce/interpreter_visitor.cpp` is called from alignment-fault handling to execute selected memory instructions. Its [visitor_base.h](https://github.com/eden-emulator/mirror/blob/943f1fc76087adcfc893fb1ca3aea507df15d004/src/core/arm/nce/visitor_base.h) returns false for ordinary unsupported arithmetic/moves; it is not a full interpreter. Use it as another semantic comparison source, retaining our checked VIXL interpreter and native differential tests. The Apple CMake path also requires desktop Carbon/Cocoa and a macOS MoltenVK library. I found no ready iOS no-JIT configuration in the inspected build/CPU paths. There are scattered `IOS` guards, which do not establish a working complete iPhone target.

## Architectural and licensing boundaries

Eden's GPU path runs the guest graphics library and emulates driver submissions: [nvhost_gpu.cpp](https://github.com/eden-emulator/mirror/blob/943f1fc76087adcfc893fb1ca3aea507df15d004/src/core/hle/service/nvdrv/devices/nvhost_gpu.cpp) accepts GPFIFO submissions and forwards command lists to `gpu.PushGPUEntries`; Maxwell/Kepler engines then drive rendering. Its `nvnflinger` is the compositor/buffer-queue service, not an implementation of our537 intercepted NVN function slots. Pulling in all of Eden's GPU therefore changes architectural scope; adapting its compiler/resource facts to our existing NVN boundary is the narrower candidate.

The repository [license](https://github.com/eden-emulator/mirror/blob/943f1fc76087adcfc893fb1ca3aea507df15d004/LICENSE.txt) and README specify GPLv3-or-later. Current files contain Eden GPL-3.0-or-later additions over older GPL-2.0-or-later or0BSD material. A direct cherry-pick must retain those notices and be evaluated under the actual combined licensing; it is not a license-neutral MIT snippet. Studying public ABI facts and implementing independently remains distinct from copying implementation. The dependency licenses also require a file-level review before adoption.

Recommended next action: use the pinned service implementation to close the next observed startup contract; in parallel, evaluate a separate headless native shader-compiler embedding experiment with original fixtures. Do not replace the CPU or full GPU architecture just because Eden already boots games on its supported platforms. No speed, memory reduction, game compatibility or App Store acceptance is established by this source review.
