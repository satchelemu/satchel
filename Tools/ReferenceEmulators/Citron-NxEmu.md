# Citron Neo and NxEmu source comparison
Read-only inspection, 2026-10-31. No dependency adopted, emulator built, game compatibility measured, or canonical project changed. Public source snapshots only.

## Provenance and pins
- Eden official Forgejo and user-supplied GitHub mirror were independently checked at the identical commit **943f1fc76087adcfc893fb1ca3aea507df15d004**. Full earlier report: [Eden source investigation](Eden.md).
- [Citron Neo website](https://www.citronneo.org/) links [citron-neo/emulator](https://github.com/citron-neo/emulator). Inspected main at **c3aa70f81e15ea97ee85b6a9a71cbf75d370851e**. Root LICENSE is GPLv3; README states GPLv3-or-later. Website platform-nightly labels are not evidence all downloads equal this source pin.
- [NxEmu website](https://www.nxemu.com/) and [N3xoX1/nxemu](https://github.com/N3xoX1/nxemu) cross-link. Inspected master at **77e0e87788f40524079b130aa8d8a5fbc3f38b62**. Root license.txt is GPLv3; individual inherited source often GPL-2.0-or-later. Preserve per-file and third-party notices when evaluating any adoption.
- These are not three independent implementations of every subsystem: Citron and Eden retain Yuzu architecture; NxEmu explicitly links yuzu_shader_recompiler, yuzu_video_core, yuzu_audio_core and yuzu_common behind its module interfaces. Novel changes need individual comparison, not brand-based claims.

## CPU and iOS
Citron root CMake enables NCE only for ARM64 Android/Linux; Apple path uses Dynarmic. Its macOS Cocoa/MoltenVK build does not establish an iOS App Store target. Sources: [CMakeLists](https://github.com/citron-neo/emulator/blob/c3aa70f81e15ea97ee85b6a9a71cbf75d370851e/CMakeLists.txt), [Dynarmic implementation](https://github.com/citron-neo/emulator/blob/c3aa70f81e15ea97ee85b6a9a71cbf75d370851e/src/core/arm/dynarmic/arm_dynarmic_64.cpp).

NxEmu is distinct: [CPU CMake](https://github.com/N3xoX1/nxemu/blob/77e0e87788f40524079b130aa8d8a5fbc3f38b62/src/nxemu-cpu/CMakeLists.txt) enables Darwin NCE on Apple ARM64 as well as Dynarmic, with Mach exception support. [CPU manager](https://github.com/N3xoX1/nxemu/blob/77e0e87788f40524079b130aa8d8a5fbc3f38b62/src/nxemu-cpu/cpu_manager.cpp) selects native execution for enabled 64-bit applications; otherwise Dynarmic. [Host memory](https://github.com/N3xoX1/nxemu/blob/77e0e87788f40524079b130aa8d8a5fbc3f38b62/src/yuzu_common/host_memory.cpp) includes executable mapping permissions. This is runtime execution of guest/native-patched code, not a full interpreter suitable for our no-dynamic-CPU-code model. No working iOS target was established by this review.

Do not import its fallback policy: [Darwin handler](https://github.com/N3xoX1/nxemu/blob/77e0e87788f40524079b130aa8d8a5fbc3f38b62/src/nxemu-cpu/nce/arm_nce_darwin.cpp#L388) explicitly skips denied accesses and unknown fallback instructions. Our checked CPU should continue to stop instead. Its Dynarmic InterpreterFallback only invokes BreakPoint. No reviewed project supplies a drop-in complete no-JIT iOS CPU.

## Ranked useful candidates
1. **Shared Maxwell compiler family, with bounded native C ABI isolation.** Eden remains the best initial source audit because its complete Environment/TranslateProgram/SPIR-V route is already documented. Citron offers largely the same compiler architecture. NxEmu’s [TranslateProgram](https://github.com/N3xoX1/nxemu/blob/77e0e87788f40524079b130aa8d8a5fbc3f38b62/src/yuzu_shader_recompiler/frontend/maxwell/translate_program.h) uses the same resource-rich Environment contract. Actual shader instructions, constants, texture layouts and stage state must be captured; an instruction pointer is insufficient. This is a potential larger on-phone shader translator, not CPU JIT or precompiled per-game shaders. Requires license choice, native dependency isolation, bounded admission and original GPU output tests before integration.

2. **NxEmu’s real geometry-to-compute lowering.** [vtg_as_compute.h](https://github.com/N3xoX1/nxemu/blob/77e0e87788f40524079b130aa8d8a5fbc3f38b62/src/yuzu_shader_recompiler/vtg_as_compute.h) defines compute output/varying layouts; [vtg_to_compute_pass.cpp](https://github.com/N3xoX1/nxemu/blob/77e0e87788f40524079b130aa8d8a5fbc3f38b62/src/yuzu_shader_recompiler/ir_opt/vtg_to_compute_pass.cpp) transforms stages, followed by a rasterizer passthrough vertex shader. More concrete than merely allowing MoltenVK with geometryShader=false. It is not a standalone tiny patch: needs buffer ownership, dispatch/draw ordering and varying semantics. Defer until actual admitted game shader requires this feature.

3. **NxEmu’s focused Metal workarounds, evaluated individually.** [moltenvk_workarounds.h](https://github.com/N3xoX1/nxemu/blob/77e0e87788f40524079b130aa8d8a5fbc3f38b62/src/yuzu_video_core/vulkan_common/moltenvk_workarounds.h) has texel-buffer offset compensation, depth-bounds admission, push-descriptor cap and attachment overlap checks. Some portions carry Ryujinx MIT attribution inside a GPL-2.0-or-later file. [DontInline patch](https://github.com/N3xoX1/nxemu/blob/77e0e87788f40524079b130aa8d8a5fbc3f38b62/external/moltenvk-patches/0001-honor-spirv-dontinline.patch) preserves explicit SPIR-V noinline in generated MSL. Its [build](https://github.com/N3xoX1/nxemu/blob/77e0e87788f40524079b130aa8d8a5fbc3f38b62/external/CMakeLists.txt#L272) pins fab918/MoltenVK fb1afa9b968226f694efa45625bb7ef90928f4df and builds macOS, not iOS. Potential fixture-driven fixes only; no measured performance benefit.

4. **Horizon time/service reference and compatibility tests.** Citron [shared page](https://github.com/citron-neo/emulator/blob/c3aa70f81e15ea97ee85b6a9a71cbf75d370851e/src/core/hle/service/psc/time/shared_memory.h) differs from Eden mainly in notices/includes. NxEmu [page](https://github.com/N3xoX1/nxemu/blob/77e0e87788f40524079b130aa8d8a5fbc3f38b62/src/nxemu-os/core/hle/service/psc/time/shared_memory.h) retains the same inherited layout. Useful corroboration, not independent firmware evidence. Their [timezone service](https://github.com/N3xoX1/nxemu/blob/77e0e87788f40524079b130aa8d8a5fbc3f38b62/src/nxemu-os/core/hle/service/psc/time/time_zone_service.cpp) can guide the next observed command; conversion still needs actual rule data and verified ABI, not a time-zone name alone.

5. **Content-aware shader cache identity design.** NxEmu [shader_profile_identity.h](https://github.com/N3xoX1/nxemu/blob/77e0e87788f40524079b130aa8d8a5fbc3f38b62/src/yuzu_video_core/shader_profile_identity.h) includes the selected base/update and cache ABI in identity. Useful future invalidation design. Its NCA size/header fingerprint is not full content integrity verification; retain our verified content-ID/section/hash provenance.

## What not to transplant
Citron [Vulkan device](https://github.com/citron-neo/emulator/blob/c3aa70f81e15ea97ee85b6a9a71cbf75d370851e/src/video_core/vulkan_common/vulkan_device.cpp) disables robustBufferAccess and robustness2 on MoltenVK. That is not an acceptable substitute for our explicit storage bounds. Nor should broad service stubs, skipped CPU faults, desktop executable-memory assumptions or website game-performance claims be treated as proven phone behavior.

All three full renderers consume emulated Tegra engines/command streams, whereas our current bridge intercepts original guest NVN calls. Sharing a compiler or a carefully tested format rule is much smaller than replacing the complete GPU architecture. NvNflinger is the compositor, not an NVN function interceptor.

## Comparison against our installed MoltenVK dependency
Our actual notice manifest pins official MoltenVK v1.4.2/db66022459ffb663aa2b50f6b018bc2e124f5edf and SPIRV-Cross6c09849fe88c48eaed08413aa022aaa136a3a057. The [exact pinned MSL source](https://github.com/KhronosGroup/SPIRV-Cross/blob/6c09849fe88c48eaed08413aa022aaa136a3a057/spirv_msl.cpp#L12117) still unconditionally emits force-inline for non-entry helpers at12129; no DontInline branch exists there. NxEmu therefore has a real source difference, but we have no measured failing workload requiring it. Keep the current official static archives. Because their SPIRV-Cross symbols are hidden, an external symbol override is not a sound integration plan. A future change would first require an original SPIR-V DontInline fixture, emitted-MSL inspection, actual iOS compile/dispatch and compile-resource measurements; only then consider an isolated reviewed rebuild. No fork or dependency change recommended now.
